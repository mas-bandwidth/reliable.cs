## 1. Wire format — MATCH

Compared the whole codec against STANDARD.md §"Packet Header"/"Fragments":
prefix bit 0 (regular 0 / fragment 1) at `Reliable.cs:530`, `:633` and `:1058`;
ack_bits-present flags bits 1-4 (set = byte present) at `Reliable.cs:442-460`
(write) and `:576-598` (read); one-byte sequence-difference flag bit 5 at
`:462-470` / `:539-548`; little-endian sequence and ack via
`BinaryPrimitives` at `:474`, `:483`, `:536`, `:556`. Fragment header is exactly
5 bytes, prefix 1, LE sequence, fragment id, count-1 at `Reliable.cs:999-1005`
(write) and `:632-642` (read). Constants `RELIABLE_MAX_PACKET_HEADER_BYTES 9` /
`RELIABLE_FRAGMENT_HEADER_BYTES 5` at `Reliable.cs:433-434`. Limits: fragment id
`< num_fragments` at `:650`, `num_fragments <= max_fragments` (256 max) at
`:644`, non-last fragment exactly `fragment_size` and last `0..fragment_size` at
`:697-707`, fragment 0 alone carries the canonical packet header at `:658-695`.
All match STANDARD.md.

## 2. Sequence buffer — MATCH

Compared `SequenceBuffer<T>` (`Reliable.cs:239-415`) with port-map item 10 and
STANDARD §"sequence arithmetic". Stale test `less(seq, sequence - num_entries)`
at `:295-303`; wrap handling in `RemoveEntries` (`finish += 65536`, bulk clear
when the range covers the buffer) at `:270-292`; `insert` advancing
`Sequence = seq+1` at `:301-315`; `advance` `:318-325`;
`insert_with_cleanup` / `advance_with_cleanup` (branch order advance-then-stale,
matching the C note) at `:329-357`; `remove` / `remove_with_cleanup` `:360-374`;
`available` / `exists` / `find` / `at_index` `:376-397`; ack-bits generation
`ack = Sequence-1`, bit i iff `exists(ack-i)` `:400-414`. Matches.

## 3. Receive path ordering and counters — MATCH (one counter-order caveat noted)

Compared the regular-packet path `Reliable.cs:1056-1164` and the fragment path
`:1166-1262` with port-map §6-8. Order is: size gate `> max+9+5`
(`:1049`) → `PacketsReceived++` (`:1062`) → header parse fail → `Invalid` (`:1065-1069`)
→ payload size gate `> max` → `TooLargeToReceive` (`:1076-1081`) → stale
`TestInsert` → `Stale` (`:1083-1088`) → duplicate `Exists` → `Duplicate`
(`:1090-1095`) → process callback → on accept: insert received, advance
reassembly with cleanup, ack walk (`:1099-1160`). Fragment path: header parse
fail → `FragmentsInvalid` (`:1182-1187`); already-received → silent drop
(`:1189-1193`); reassembly insert stale → `FragmentsInvalid` (`:1199-1206`);
count mismatch → `FragmentsInvalid` (`:1224-1229`); duplicate fragment → silent
drop (`:1231-1235`); delivery then `FragmentsReceived++` at `:1261`. The eleven
counters and their order are the C order index for index
(`EndpointCounter` `Reliable.cs:116-140`): sent, received, acked, stale,
invalid, too_large_send, too_large_receive, fragments_sent, fragments_received,
fragments_invalid, duplicate. Matches.

## 4. Replay and window semantics — BUG

Checklist: C now moves the received window **only when a packet is accepted**; a
fragment never moves it. The port still advances the received-packet window from
the fragment path: `_receivedPackets.Advance(sequence)` at
`Reliable.cs:1208`, reached on the first fragment of a packet that is not yet in
reassembly. C (fixed) does not advance the received window for a fragment —
`C line unread` (audit: the fragment insert path in `reliable.c`; the fix lands
on `sprint/reliable-audit-fixes`). Impact: a far-ahead fragment moves the
received window forward and can then mark a genuine, in-order regular packet as
stale, diverging from C. A card would delete the `Advance` at `Reliable.cs:1208`
and rely on the reassembly buffer's own window; see item 9.

## 5. Malformed input — BUG (empty receive) and MATCH for the rest

- Zero-length receive: the port throws `ArgumentException` at
  `Reliable.cs:1040-1045` (`if (packetData.IsEmpty) throw`). The audit records
  that C counts the packet invalid instead of refusing via an assert.
  `C line unread`; the audit candidate names this explicitly. If C counts it
  invalid, the port must not throw on wire data — `BUG`. The differential
  `malformed` mode feeds a zero-length vector precisely to decide this; with no
  C reference it stays open.
- Oversize: `packetBytes > max + 9 + 5` → `TooLargeToReceive` and return, no
  read past the header, `Reliable.cs:1049-1054`. Matches.
- Truncated headers: `ReadPacketHeader` returns -1 at `:520`, `:541`, `:551`,
  `:568`; `ReadFragmentHeader` at `:624`. No throw, no read out of bounds.
  Matches.
- Bad fragment counts: `fragment_id >= num_fragments` `:650`, `num_fragments >
  max_fragments` `:644`, count mismatch `:1224`. Matches.
- Fragment-buffer size computation can overflow: `Wire.MaxPacketHeaderBytes +
  numFragments * _fragmentSize` at `Reliable.cs:1210` (and
  `(NumFragmentsTotal - 1) * fragmentSize` at `:1294`) are `int`; with a very
  large `FragmentSize` (config does not bound it — item 6) the product overflows
  and the subsequent `Rent`/write bounds are wrong. `BUG` at
  `Reliable.cs:1210` vs the C's checked config bound `max_fragments *
  fragment_size <= INT_MAX - 9` (`C line unread`).

## 6. Config validation and defaults — BUG

Defaults match C exactly: `Reliable.cs:161-197` — max packet 16 KiB,
fragment_above 1024, 16 fragments of 1024, ack buffer 256, sent/received 256,
reassembly 64, rtt smoothing 0.0025, rtt history 512, loss 0.1, bandwidth 0.1,
header 28. `MATCH` on defaults.

Validation is weaker than `reliable_config_valid`. Constructor checks
(`Reliable.cs:839-865`) cover only `> 0` for the sizes, `MaxFragments in
[1,256]`, callbacks non-null, and the fragment-cover rule. It does **not** refuse:

- `fragment_above > max_packet_size` — `BUG` (absent; `Reliable.cs:842,856`).
- `max_fragments * fragment_size <= INT_MAX - 9` — absent, the overflow in item 5.
- `max_packet_size <= INT_MAX - 14` — absent.
- `packet_header_size >= 0` — absent (`:881` copies it unvalidated).
- `header + max_packet_size <= INT_MAX` — absent.
- power-of-two sequence-buffer sizes up to 16384 — absent; the C spec requires
  the sent/received/reassembly buffers be powers of two (`C` `reliable_config_valid`).

Port site: `Reliable.cs:839-865`. C site: `reliable_config_valid` (`C line
unread`; audit records the five missing clauses). The port's fragment-cover rule
already applies only when `MaxPacketSize > FragmentAbove` (`:856`), matching the
audit's note. A card would add the missing refusals to the constructor.

## 7. Statistics — BUG

- `Reset` does not clear the statistics or refill the rtt history. The port's own
  doc comment (`Reliable.cs:1330-1335`) claims C also leaves smoothed stats
  alone, but the checklist (item 7) states C's `Reset` clears every statistic and
  fills the rtt history with -1. `Reset` at `Reliable.cs:1336-1355` clears acks,
  counters, sequence and the three buffers only; it does not reset `_rtt`,
  `_rttMin/_rttMax/_rttAvg`, the jitter fields, `_packetLoss`, the three
  bandwidth fields, nor `_rttHistoryBuffer`. `BUG` vs the C `reliable_endpoint_reset`
  (`C line unread`; audit cites `reliable.c:1540-1559`).
- rtt minimum uses the sentinel `10000.0f` (`Reliable.cs:1367` and the reset to 0
  at `:1388`) where C decides emptiness by a count. A genuine sample of exactly
  10000.0 ms would be coerced to a 0 minimum. `BUG`/`DIVERGENCE`, port
  `Reliable.cs:1367,1388`; C `reliable.c` `reliable_endpoint_update` (`C line
  unread`).
- Bandwidth byte sums are `int` (`Reliable.cs:1519`, `:1559`, `:1603`) where C
  uses a 64-bit accumulator; a `> 2 GiB` sample window overflows. `BUG` at those
  lines.
- Note for the gate: the port's `(float)`/`Math.Pow`/double promotions
  (`:1458`, `:1531`, `:1571`, `:1615`) and `-ffp-contract=off` on the C build
  are what keep bit-exact output; the interop gate covers this (item 10).

## 8. Memory — DIVERGENCE

- Reassembly buffer: rented from `ArrayPool<byte>.Shared` at
  `Reliable.cs:1215` and **not zeroed**; C 1.4.5 zeroes the buffer
  (`reliable.c` `reliable_fragment_reassembly_data_*`, `C line unread`). The
  delivery read is `[9-header_bytes, 9+packet_bytes)` and every byte in that
  range is written from fragments, so no uninitialised byte is delivered in the
  exercised cases; the divergence is determinism/parity with C's zeroing, not a
  read of garbage. `DIVERGENCE` (allowed: pooled allocation is the family's
  stated zero-alloc choice, `Reliable.cs:23`), port `Reliable.cs:1215`.
- No `+8` slack on the rented buffer — the port writes up to
  `9 + numFragments*fragmentSize` (`:1210`, `:1299`); C's slack is tied to its
  zeroed layout. `DIVERGENCE`, same site.
- Config name: port stores a managed `string` (`Reliable.cs:155`, `:783`), so it
  is inherently NUL-safe; C copies into a fixed `char name[]`. `MATCH` on safety.
- Allocation failure: `ArrayPool.Rent` does not return null on failure as C's
  `malloc`-check does; there is no "refused and counted" path for a reassembly
  rent. `DIVERGENCE` (allowed under GC), port `Reliable.cs:1215`.
- Unfinished-reassembly byte budget (the change C is adding): not present in the
  port. `QUESTION` — needs the C `sprint/reliable-audit-fixes` read to state the
  exact budget and counter.

## 9. C follow-up: fragment_reassembly window on a first fragment — MATCH (bug-for-bug)

The C follow-up records that `fragment_reassembly` still advances **its own**
window on a first fragment, so a far-ahead unfinished fragment can stale a
genuine fragmented packet still in reassembly. The port reproduces that:
`InsertWithCleanup(sequence, _reassemblyCleanup)` at `Reliable.cs:1199`
advances the reassembly buffer's window (via `:331-335`), independent of item
4's received-window `Advance` at `:1208`. Port matches C's known behaviour at
`Reliable.cs:1199`; C `reliable.c` fragment receive path (`C line unread`).
Recorded so the next audit can decide whether to carry the C follow-up fix into
the port as well.

## 10. Interop pin and vendored reference — BUG / DIVERGENCE

- The interop gate is pinned to release tag **v1.4.0** (`.github/workflows/ci.yml`
  and the `scripts/interop.sh` header, `notes/port-map.md:4`), but the C fix this
  card compares against is `sprint/reliable-audit-fixes` at/after `7862477e`.
  `DIVERGENCE`: the pin tests a C commit that predates the audit fixes, so parity
  with the current reference is not proven. A card would bump the pin.
- The hostile scenario never calls `Reset` and never exercises the config edges:
  `run_scenario` in `compat/c/compat.c:346-509` and `RunScenario` in
  `compat/Compat.cs:309-459` send only traffic, corruption, duplication and
  injection; no `Reset`, no invalid config. `BUG`/coverage gap at those sites.
- STANDARD.md drift: the audit reports the vendored copy has drifted from
  upstream by 65 lines and CI's spec-sync step would fail. `QUESTION` — needs
  the upstream `STANDARD.md` to diff (no C checkout here).
